# Релиз — локальный `/release` с push после подтверждения, GitHub Release — Action по тегу

Релиз выпускает только владелец, и он хочет видеть номер, название и описание до публикации. Поэтому Релиз собирается локально скиллом `/release`: скрипт вычисляет версию из Conventional Commits и собирает черновик, агент переписывает его на английском, пользователь подтверждает на стоп-гейте, после чего скрипт делает релизный коммит, аннотированный тег и `git push --atomic origin main vX.Y.Z`. GitHub Action по тегу только публикует Release с телом из `CHANGELOG.md`, вызывая тот же скрипт (`-Notes`), чтобы логика была одна и покрыта тестами. Это единственное исключение из правила «push делает только человек»; force-push запрещён всегда.

## Considered Options

- **release-please / semantic-release в облаке.** Отклонено: Релиз-PR создаётся на каждый merge, текст пишется машиной без человеческой редактуры и без стоп-гейта; лишняя зависимость.
- **`/release` без push, push руками.** Было исходным решением интервью; пересмотрено пользователем: ручной шаг ничего не добавляет к уже подтверждённому стоп-гейту.
- **Ручные GitHub Releases.** Отклонено: CHANGELOG и Releases расходятся.

## Consequences

- Ruleset на `main` должен разрешать bypass владельцу, иначе релизный коммит не запушится.
- Ошибка push оставляет локальные коммит и тег; `-Undo` работает только до push, после — исправляющий PATCH.
- Скилл `release` — только для Шаблона; `Initialize-Project` не переносит его в Проекты.
