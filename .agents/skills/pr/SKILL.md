# Pull Request — Description Formatter

Format a concise, high-signal Pull Request (or Merge Request) description following the **Show-Me / Evidence / Merge Danger** framework. The goal is to give reviewers immediate clarity on what changed in under 30 seconds, prove correctness with observable evidence, and make deployment risks transparent.

## The Three Core Sections

Every PR description generated by this skill must include three structured sections:

```markdown
## Summary

<Show-Me visual snapshot: pseudocode, call tree, file tree, Mermaid, or diff sketch>

- <Bullet 1: Why this change was made>
- <Bullet 2: Key architectural decision or trade-off>

## Evidence

### Before
<Console output of failing test (red), error log, or visual state before change>

### After
<Console output of passing test (green), clean execution, or visual state after change>

- Verification command: `<exact command run>` (exit code <N>, <N> passed)

## Merge Danger

- **Door:** one-way | two-way
- **Blast Radius:** <Specific modules, workflows, or users affected if this fails; what remains insulated>
```

---

### 1. `## Summary` (The Show-Me Principle)

Reviewers should not have to reverse-engineer architecture or intent by reading a long narrative wall of text. Adapt Dex Horthy's **Show-Me** principle: lead with a visual or conceptual representation that communicates the essence of the change in 5 seconds.

Select the format best suited to the change:
- **Pseudocode or usage snippet:** Demonstrates how callers interact with the new or modified API before and after.
- **ASCII call tree or pipeline flow:** Illustrates function call sequences or data pipelines.
- **Shallow file tree:** Highlights key directory additions, renames, or architectural seams.
- **Mermaid diagram:** Renders a sequence (`sequenceDiagram`) or state machine (`stateDiagram-v2`) for complex interactions.
- **Targeted diff sketch:** Isolates the single critical contract change, omitting surrounding boilerplate.

Follow the visualization with 2–4 concise bullet points explaining the core rationale and architectural tradeoffs. Anchor domain terms to [`.agents/CONTEXT.md`](../../CONTEXT.md).

---

### 2. `## Evidence` (Observable Proof)

Reviewers must not rely on assumptions of correctness. Provide concrete, verifiable evidence in a **Before / After** pair:

- **Bug fixes:** The failing test output or error reproduction log (**Before**) contrasted with the green test execution or clean output (**After**).
- **Features and refactors:** The missing capability or prior behavior (**Before**) contrasted with the new test suite or feature verification (**After**).
- **Performance optimizations:** Benchmark figures, memory allocations, or timing measurements before vs after.
- **Visual or UI changes:** Screenshots or ASCII terminal representations showing the prior state vs updated layout.

Always record the exact test commands used and results (e.g. `pwsh -File .agents/scripts/Test-Template.ps1` -> exit code 0).

---

### 3. `## Merge Danger` (Reversibility and Blast Radius)

Explicitly assess deployment safety and failure impact across two dimensions:

#### Door: One-Way vs Two-Way
- **Two-way door:** Easily reversible change with low rollback cost. Examples: additive code, new helper functions, features behind a feature flag, or changes encapsulated within an existing module seam. Reverting causes no data loss or external disruption.
- **One-way door:** Irreversible or high-friction rollback. Examples: database migrations dropping columns/tables, breaking changes to public API contracts, destructive data transformations, or external webhook changes. Requires explicit rollout steps or backward-compatible migration phases.

#### Blast Radius
Define precisely which components, downstream services, or user flows could fail if this change introduces a regression:
- State what is exposed: e.g. *"CLI argument parsing for batch exports."*
- State what is insulated: e.g. *"Zero impact on background job processing, database transactions, or HTTP API endpoints."*

## Hard Guardrails

### 1. No Unauthorized `git push`

> [!CAUTION]
> **Do not run `git push` under any circumstances.**

In StrataHarness, publishing and pushing code to remote repositories is strictly reserved for the human developer. The single exception across all skills is the `/release` command, which executes a push only after explicit user confirmation at its stop gate.

### 2. Output Destination

- Default behavior: Print the complete, formatted PR description directly into the conversation chat, or save it to `.scratch/PR.md` (or `.scratch/<feature>/PR.md`) for the user to review, edit, and copy.
- Do NOT attempt to publish the PR automatically.

### 3. PR Creation Tools (`gh` / `glab`)

- Only run `gh pr create` or `glab mr create` if the user **explicitly commands it** (e.g. *"create the PR using gh"*, *"открой PR через glab"*).
- Before invoking CLI tools:
  1. Check that the CLI tool is installed and authenticated (`gh auth status` or `glab auth status`).
  2. Confirm the remote branch has already been pushed by the user.
  3. Never pass `--push` flags or attempt to push the branch yourself.
